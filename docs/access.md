# Авторизация и видимость

| Посетитель | Доступ |
|---|---|
| Без входа | Обзор, проекты, зависимости, образы, CI-компоненты и webhook |
| Пользователь | Публичные каталоги, личные группы видимости и просмотр состояния сканирования |
| Администратор | Запуск сканирования, пользователи, требования, параметры, языки, фреймворки, политики видимости и черный список |

## Настройка OIDC

Авторизация обязательна для управляющих функций. Публичные страницы доступны без входа и без ограничений
видимости. У OIDC-провайдера требуется confidential client:

- Authorization Code flow — включен;
- PKCE с методом `S256` — включен;
- аутентификация клиента через `client_secret` — включена;
- redirect URI — `https://<application-host>/api/auth/callback`;
- post logout redirect URI, если провайдер поддерживает RP-initiated logout, — `https://<application-host>/`.

Backend обращается к провайдеру по внутреннему адресу и хранит токены на сервере.
Провайдер должен возвращать подписанный `id_token` с claim `preferred_username`.

Issuer задается одним из двух способов:

```dotenv
# Приоритетный вариант для любого OIDC-провайдера
RADAR_AUTH_ISSUER=https://gitlab.com
RADAR_AUTH_INTERNAL_URL=https://gitlab.com
```

или через совместимые с прежней конфигурацией параметры Keycloak:

```dotenv
RADAR_AUTH_PUBLIC_URL=https://keycloak.example.com
RADAR_AUTH_INTERNAL_URL=http://keycloak:8080
RADAR_AUTH_REALM=example
```

Если задан `RADAR_AUTH_ISSUER`, значения `RADAR_AUTH_PUBLIC_URL` и `RADAR_AUTH_REALM` игнорируются.
`RADAR_AUTH_INTERNAL_URL` задает адрес того же провайдера, доступный backend. Для прямого issuer его путь
сохраняется, меняется только origin; если отдельного внутреннего адреса нет, укажите тот же адрес провайдера.

Первоначальный список администраторов задается через запятую по claim `preferred_username`:

```dotenv
RADAR_AUTH_PREFERRED_USERNAMES=user.one,user.two
```

Список должен содержать хотя бы одного пользователя.

Любой пользователь OIDC-провайдера может войти в приложение и автоматически добавляется в список
пользователей без административных прав. Администраторы назначают роли и блокируют пользователей в разделе
«Пользователи»; там же можно заранее добавить или удалить локальную запись. Удаленный пользователь снова
появится после следующего входа, поэтому для запрета доступа используется блокировка. Роль пользователей из
`RADAR_AUTH_PREFERRED_USERNAMES` управляется через окружение.

Отключенного пользователя не авторизует OIDC-провайдер. Для немедленного запрета доступа пользователю с уже
выданной сессией используется блокировка в приложении.

## Правила видимости

Видимость фильтрует пользовательское представление каталога по пути проекта или языку.
Публичный каталог доступен без этих ограничений: политики не являются границей доступа к данным.
Заблокированный пользователь теряет управляющие функции, но публичные данные остаются доступны.

Пользователь выбирает личную группу правил. Администратор назначает политики и индивидуальные правила.
Внутри набора `include` выбирает подходящие проекты, `exclude` исключает их; фильтры пути и языка
применяются последовательно. Несколько назначенных политик объединяются, затем учитываются
индивидуальные административные правила и выбранная личная группа.

Черный список действует независимо от видимости и исключает проект из сбора и выдачи для всех:
[правила сканирования](scanning.md).

## Сессии

Браузер использует серверную сессию и CSRF-токен для изменяющих запросов. Параллельные запросы
одной сессии обновляют OIDC-токены последовательно. WebSocket подключается по краткоживущему
одноразовому билету, выданному после авторизации.
