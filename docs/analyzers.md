# Анализаторы

Перед анализом проверяются кодировка, синтаксис структурированных файлов и основные секции зависимостей.
Отсутствующий файл не считается ошибкой; корректный пустой файл отличается от поврежденного.
Ошибка одного файла или модуля не удаляет успешные результаты других модулей. Диагностика содержит
путь и тип проблемы, без фрагментов конфигурации, которые могут содержать секреты.

## Форматы

| Источник | Разбор и ограничения |
|---|---|
| Python | TOML через `tomllib`, спецификаторы через `packaging.Requirement`; включения dependency-groups разрешаются. Ссылки на дополнительные requirements/constraints отмечаются как частичный разбор |
| Maven | Структурный XML, namespaces, properties, локальный dependencyManagement. Внешние parent/BOM не скачиваются, profiles не активируются; неразрешенные версии отмечаются диагностикой |
| Gradle | Статическое извлечение литеральных координат и version catalog. Скрипты не исполняются; обнаруженные вычисляемые зависимости отмечаются диагностикой. Это не полная проверка синтаксиса Groovy/Kotlin |
| npm | Lock v1 для самостоятельного проекта; v2/v3 — обход графа от записи модуля, включая вложенные node_modules и workspace links |
| pnpm | Lock v5/v6/v9: обход от importer через packages/snapshots, включая локальные links. Другие версии отмечаются как неподдержанные |
| Yarn | Classic v1 и YAML lock с metadata v4–v8: обход от объявлений модуля по дескрипторам. Если ссылка не разрешена, общий список пакетов не приписывается модулю |
| Compose / GitLab CI | Безопасный YAML-разбор; для CI поддерживается тег `!reference`, но внешние include и итоговая конфигурация pipeline не вычисляются |

Для Node выбирается ближайший lock-файл в каталоге модуля или его предках. Если в одном каталоге
их несколько, используется приоритет npm-shrinkwrap, package-lock, pnpm, Yarn и выдается предупреждение.
Синтаксически поврежденный локальный lock не заменяется молча родительским. Peer-зависимости остаются
объявлениями manifest; их автоматическое разрешение не выполняется.

XML entities и DTD не поддерживаются. Репозиторные build-скрипты и пакетные менеджеры не запускаются,
сеть для разрешения зависимостей не используется.

## Повторное использование

Снимок с частичным результатом пригоден для отображения, но содержит ошибку и не допускается к reuse.
Ошибки файлов и языков попадают в список ошибок запуска. При переносе отсутствующего проекта
сохраняется признак частичного результата. При изменении логики разбора версии анализаторов и общий fingerprint должны обновляться,
чтобы прежние результаты не обходили новые проверки.

## Выбор библиотек

Используются `tomllib`, `json`, `defusedxml` с запретом DTD/entities,
`packaging` и безопасный loader PyYAML. Библиотеки отвечают за синтаксис; адаптеры — за семантику
модулей и графов. Универсальную замену на ScanCode не вводим: его широкий набор парсеров сам по себе
не подтверждает нужное разрешение workspace и совместимость всего набора зависимостей с Python проекта.
Отдельный Yarn v1-only parser не покрывает все используемые форматы.

Справочные источники: [packaging](https://packaging.pypa.io/en/stable/requirements.html),
[npm lock](https://docs.npmjs.com/files/package-lock.json/),
[pnpm lock](https://github.com/pnpm/pnpm.io/blob/main/docs/lockfile.md),
[ScanCode](https://github.com/aboutcode-org/scancode-toolkit).

## Состав результата

Python определяет модули, версию из `.python-version` или ограничение `requires-python`,
uv/pip, зависимости, registry и настроенные инструменты. Java формирует модули по Maven POM
или Gradle build-файлу. Node формирует модуль по каждому `package.json`, определяет менеджер,
версию из `engines.node`, `.nvmrc` или `.node-version`, зависимости и registry.
Общие файлы Docker и GitLab CI анализируются независимо от языка.

Входные файлы и жизненный цикл результата: [сканирование](scanning.md).
